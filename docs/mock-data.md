# Session mock data

Create one `createMockData()` instance in the application provider and inject its `port` into screens. Never import fixtures from a component. The instance owns one in-memory ledger shared by all routes; reload or `demo.reset()` deliberately loses session changes. There is no browser storage, database, email, payment or authentication provider.

The asynchronous `DataPort` offers snapshot queries, current/historical expense queries, commands, operation lookup and change subscriptions. Queries return isolated copies. Screens must invalidate/requery on notifications and ignore obsolete request responses using a request sequence; they must not serialize previous financial results into navigation state. Mutations continue after screen unmount. The mock commits a complete cloned state in one synchronous step after validation and aggregate checks; notification errors cannot turn a committed write into a failed command.

Commands supply household ID and a stable client operation ID; the actor comes from the adapter context. Retain the same operation ID and unchanged payload through retries of an unknown outcome. Successful operations are bound to that actor/household and canonical payload; changed payload reuse is rejected. Validation and version rejection do not commit or reserve the ID, so corrections can be resubmitted. Operations cannot be inspected by a different actor. Deletions retain full snapshots, creator identity, actor, reason and stable record URL. Activity uses timestamps plus sequence rather than effective date.

`demo` is a separate development interface with named scenarios: normal, slow, denied, expired, offline, timeout-after-commit, second-editor and concurrent-delete. Transient command scenarios are consumed by the next command; denied/expired remain until explicitly changed. Offline reads remain unavailable until recovery or the next attempted command consumes that scenario. `second-editor` and `concurrent-delete` create real simulated audit revisions before rejecting the stale caller. Use `operation()` after an unknown outcome before retrying. Reset invalidates pending work and clears operation history, revisions, sequence and actor selection.

Fixtures are `sample`, `empty`, and `three-members`; all use the same service. The sample clock is September 20, 2026, and all documented totals are contract-tested. Clock, unique ID source and slow-delay scheduler can be injected. The ID source must return unique opaque IDs; the default is deterministic and resets with the fixture. Seed access checks simulate actor, household, active membership and owner-only household edits at the port boundary. They provide **no actual privacy or server authorization**. Membership/invitation commands will extend this boundary in the dedicated access issues.

Run `pnpm test` for the reusable port contracts, including success, validation, duplicate payloads, before/after-commit failure, stale revisions, concurrent deletion, denial, snapshot isolation and reset during delayed requests. A future API adapter should run equivalent contracts against its authorized transport and durable atomic storage.
