# Targeted invitation operations

Issue #79 implements the targeted critical path approved in [ADR-006](decisions/006-invitation-onboarding-design.md). The Go service, migration and restricted database functions are internal application boundaries. [Onboarding](onboarding.md) adds the #80 Auth/provider adapters, email transport, reviewed invitation SDL and browser experience over this service. The existing expense API remains intact; the [Relay expense journey](relay-expenses.md) connects the authenticated financial browser; the seeded preview routes were retired in #184. Reusable shared links reuse this model as described below.

## Provider adapter contract

Construct `invitation.New(db, protector, provider)` from `apps/api/internal/invitation`, using the existing restricted `database.DB`, a backend-only `NewProtector(currentVersion, keyring)`, and an `auth.CurrentEmailProvider`. Run requests through the existing #78 verifier before invoking authenticated operations. Never bind subjects from GraphQL inputs or browser metadata. A nil email provider permits owner operations but fails acceptance closed.

| Internal operation                                          | Contract for the adapter                                                                                                                                                                                                  |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Create(ctx, group, email, key)`                            | Current enabled owner only. Returns `SAVED` or `EXISTING`; duplicate targets do not renew or send.                                                                                                                        |
| `List(ctx, group, after, limit)`                            | Owner-only projection, capped at 50, exclusive UUID cursor. Recipient exists only while outstanding; safe latest delivery action/status is included, never a token. Refresh pagination to discover concurrent insertions. |
| `Resend(ctx, group, invitation, key)`                       | A deliberate new action renews the same token for seven days. Retry with the original key to recover without renewing again.                                                                                              |
| `Revoke(ctx, group, invitation, key)`                       | Terminal revocation clears recipient/token data and suppresses retryable delivery. It does not remove an admitted membership.                                                                                             |
| `Recover(ctx, operation, key)`                              | Same authenticated actor and current authority. Operation is `CREATE`, `RESEND`, `REVOKE` or `ACCEPT`. `NOT_OBSERVED` is not proof an in-flight commit cannot succeed.                                                    |
| `Preview(ctx, token)`                                       | A currently valid capability reveals exactly group name and inviter display name. It does not consume the invitation or authorize group reads.                                                                            |
| `Eligible(ctx, token, email)`                               | Narrow boolean for the constrained invite-eligible Auth provisioning adapter. Never publish it as account-existence lookup; it grants no membership.                                                                      |
| `Accept(ctx, token, key)`                                   | Atomically provisions an application identity if needed, admits/reactivates the stable membership and consumes the invitation. Requires fresh matching verified-email evidence.                                           |
| `Claim(ctx, actionID)` / `Complete(ctx, dispatch, outcome)` | Trusted server-side delivery handoff, outside browser responses. Claim commits before the adapter sends; completion uses the exact opaque dispatch.                                                                       |

Generate and retain an operation UUID before the first write. Retrying the same actor/operation/key with changed canonical inputs returns `KEY_REUSED`. Keep the original key across timeout, navigation and uncertain completion. A successful result separates `ExpiresAt` (the action's committed expiry) from `CurrentExpiresAt`, current lifecycle/delivery and current `HasAccess`. An error never confirms a commit. Historical membership IDs and `HasAccess` are not access credentials; subsequent group reads must independently authorize through the existing database boundary.

Disabled identities remain denied by the verified transaction helper, including receipt recovery. An enabled former member may recover a historical acceptance with `HasAccess=false`; recovery never reactivates membership. Another actor cannot retrieve the receipt. SQL/provider details are reduced to safe outcomes. The public adapter must map expected outcomes and unavailable dependencies deliberately rather than blindly serialize internal structs, errors or provider data.

## Current email and identity

`CurrentEmailProvider.CurrentEmail(ctx, verifiedSubject)` is a trusted server dependency, not a client proof. The onboarding adapter implements it with a fresh request to the configured Supabase Auth service using the same request's access token, return the provider's actual subject/current email/verification status, and check provider errors. It must not use JWT email claims, user metadata, pending email, a profile cache or a privileged database lookup. Request-scoped adapters may capture that request's access token; never share one user's token in a global service.

`auth.ObserveCurrentEmail` binds opaque evidence to the private verified-request marker. Derived contexts remain valid; another request, even for the same subject, cannot reuse it. Acceptance checks the five-second monotonic budget after database locks and again before committing. An over-budget attempt rolls back, observes again outside locks and retries at most twice. `VERIFY_EMAIL`, `WRONG_ACCOUNT`, invalid authentication and unavailable verification are distinct outcomes.

The observation is sampled current provider state, not an atomic transaction with Supabase email changes. A provider change after observation can race admission within this bound. The adapter must retain this documented limitation; another HTTP lookup does not make the systems atomic.

The common canonicalizer trims outer Unicode whitespace and lowercases supported ASCII addr-specs; it preserves dots and plus aliases and rejects display names, quoted local parts, internal whitespace/control characters and unsupported internationalized syntax. No email-based account merge occurs. The database has no email-to-identity directory, so create cannot safely determine that an address already belongs to an active member. Acceptance by an already-active member consumes the invitation without changing that membership or its existing role. #80 may avoid unnecessary invitations only using trustworthy provider information, never a guessed identity mapping.

## Persistence and races

The migration adds invitation/action/delivery tables with RLS enabled and no direct runtime table grants. Narrow fixed-search-path functions enforce current ownership, token validity and admission; browser roles cannot execute them. Existing user locks precede the group lock, followed by invitation/action and membership changes. Subject/action serialization protects first provisioning and retries across instances. Decisions use `clock_timestamp()` after lock waits, not transaction-start time. At equality with expiry the invitation is invalid.

One outstanding recipient per group includes expired rows. Create/resend expiry is seven days from the serialized decision. Accepted/revoked records never revive; acceptance-first leaves membership in place when later revoke reports already accepted. Revocation-first denies admission. A failed acceptance rolls back application-user provisioning, membership and action changes together.

A membership departure receives a monotonic order value. An inactive member needs a newly created targeted invitation after that departure; resending an older invitation does not change its issuance order. Readmission preserves the membership ID and restores ordinary membership/full-history eligibility without changing owner or designated-creator pointers. Future departure/transfer implementations must respect the same user/group locking protocol. The existing [persisted expense reads](persisted-expenses.md) authorize through this stable membership boundary; #79 adds no financial service.

## Token, delivery and retention

Tokens use 32 CSPRNG bytes encoded as unpadded base64url. The database stores a SHA-256 lookup hash and an AES-256-GCM recoverable copy bound to invitation ID/purpose. Missing keys, tampering and randomness failures fail closed; they never generate a replacement token for an existing invitation. Keep encryption and digest key versions in backend secret configuration, outside the database/browser/repository. New writes use the current version; retain old versions while outstanding ciphertext or retained HMAC action comparisons reference them. Token-preserving re-encryption uses the same plaintext, not a new capability.

Recipient comparison data and recoverable token ciphertext remain while outstanding, including expired invitations. Acceptance/revocation removes both from the live invitation. Minimal actor-bound action/admission metadata and keyed input digests remain for audit and duplicate safety. This is not an assertion that backups or previously transmitted email have been erased.

Creation/resend commits the delivery intent and encrypted immutable snapshot in the same transaction as the invitation/action. The snapshot schema is `recipient`, `token`, `expiresAt`, `template` (`targeted-v1`). The original action expiry and payload remain unchanged by later resends. `Dispatch.Payload()` returns a copy only to the trusted sender; the type redacts diagnostic formatting. `Dispatch.ProviderKey()` is stable for that action. Delivery adapters must preserve versioned template rendering and configured link origin across retries so identical action keys send identical provider payloads. Never derive link origins from untrusted host headers.

Claim uses a 30-second lease and records `UNKNOWN` before returning sensitive material. Call Resend outside database locks with a timeout shorter than the lease, then complete with `PROVIDER_ACCEPTED`, `FAILED_DEFINITE` or `UNKNOWN`. Provider acceptance is not recipient delivery. Definite failures and uncertain sends retry the same action/payload/key; a deliberate later resend gets a new action/provider key. A stale completion cannot overwrite a newer lease or terminal suppression. Current owner authority is checked again; a new owner must use a new authorized resend rather than recover another actor's action.

Recovery stops conservatively at 23 hours from first submission, within the provider's documented 24-hour deduplication window. An intent never submitted also has a 23-hour pending-material deadline. Expired invitations require deliberate resend rather than email-only recovery. After the recovery window ends, recover state and ask for a new deliberate action; never blindly retransmit the old intent. Accepted/revoked transitions suppress retries, and provider-accepted completion purges the snapshot. The server runs `DB.RunInvitationMaintenance` at startup and every minute with bounded calls, cancellation and shutdown joining. It purges expired material even without invitation traffic; claims independently enforce the deadline during outages.

Deliberate sends are limited transactionally to one per invitation per minute and ten per group per hour. A denied rate-limited action does not renew expiry. Same-action recovery does not consume another budget. Public adapters must additionally protect public capability/Auth endpoints with request/IP budgets and enumeration-safe responses before provider calls. No automatic delivery worker, retry schedule, atomic database-plus-email transaction or exactly-once delivery guarantee is claimed.

## Verification boundary

`make db-test` applies upgrade and fresh replay, compares desired schema, checks restricted roles and runs race-enabled real PostgreSQL tests including invitation operations. Tests exercise concurrent create/accept, both orders of competing lifecycle changes, rollback, old-link/readmission denial, evidence expiry across a lock wait, delivery recovery/leases/purge and ownership changes. Crypto tests cover token format, entropy failures, tampering, unavailable keys and versioned key handling. Local Auth compatibility tests use synthetic accounts only; production getUser adapters, verification/recovery callbacks, SMTP/Resend transport and browser behavior remain #80 responsibilities.

Onboarding must keep public signup disabled, preserve invitation eligibility and current-email checks at final acceptance, validate callback destinations and session transitions, apply the approved 15-minute/current-session logout policy, and publish only implemented reviewed SDL. It must consume this service rather than insert memberships or duplicate lifecycle state. Current provider/browser integration is described in [onboarding](onboarding.md).

## Reusable shared links

Issue #108 adds `CreateShared`, `RenewShared`, and `CopyShared` over the same invitation rows, actor-bound action receipts, owner locks and verified `Accept` boundary. Owners can create/retrieve a shared link, explicitly copy it, renew it, or revoke it from the invitation management page. There is one non-revoked shared link per group, including when expired. Repeated creation and copying do not change expiry. Explicit renewal retains the exact token and sets expiry to seven days from the serialized decision; same-key recovery never renews twice. Revocation is terminal and requires deliberate creation of a replacement. Management follows the current enabled owner after transfer. None of these operations schedules application email.

A shared capability previews invitation kind, group name and inviter display name, using the same public projection as targeted invitations. Registered, signed-in users with freshly verified current email can explicitly Join. Under #164, a live eligible shared context may start first-time account creation with independent email verification. Public signup remains disabled; shared-link possession never proves an email address. Forwarded recipients follow the same rules; there is no use cap or approval queue. Admission creates ordinary membership with normal full-history access, without consuming or renewing the link or granting group creation or ownership. Existing active members get ALREADY_MEMBER; every inactive/former membership is denied with NEW_TARGETED_INVITATION_REQUIRED, even after renewal or replacement. Expiry and revocation deny future joins and leave existing memberships intact.

Safe lists expose the invitation kind but no token. The authenticated `POST /onboarding/copy-shared` endpoint accepts public group/invitation IDs, checks current ownership, and returns the configured-origin `/join#` link under `Cache-Control: no-store` and `Referrer-Policy: no-referrer`. The browser writes it directly to the clipboard and never renders it or stores it in session/local storage. Token ciphertext uses the existing keyring with SHARED purpose binding; diagnostic formatting is redacted. Shared-link receipt recovery uses CREATE_SHARED and RENEW_SHARED in the existing SDL.

The additive migration extends existing constraints and functions; it does not rewrite memberships or financial history. Targeted delivery and targeted readmission remain unchanged. #164 supersedes the original signup restriction with the constrained verification flow documented in [onboarding](onboarding.md). Shared lifecycle tests cover duplicate/concurrent joins, copy/renew expiry stability, terminal revocation, no delivery records and same-token reuse; independent tests cover the additional authorization and race boundaries.
